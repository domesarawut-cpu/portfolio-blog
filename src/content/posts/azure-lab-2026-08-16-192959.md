## Résumé pour la direction

### Scenario

L’équipe Nautilus DevOps avait besoin de provisionner une nouvelle machine virtuelle Linux dans Azure pour répondre à un besoin opérationnel immédiat. Dans ce contexte, l’accès au portail Azure était restreint, ce qui imposait une approche entièrement en ligne de commande depuis l’hôte `azure-client`.

Cette contrainte a renforcé une pratique alignée avec les standards modernes d’exploitation cloud : privilégier une gestion headless et orientée Infrastructure as Code plutôt qu’une administration manuelle par interface graphique. L’objectif était de déployer rapidement une VM conforme aux paramètres demandés, tout en garantissant la traçabilité de l’action, la reproductibilité du processus et la validation de l’état final de la ressource.

Les exigences transmises étaient les suivantes :

- Nom de la VM : `devops-vm`
- Système : `Ubuntu2204`
- Taille : `Standard_B2s`
- Compte administrateur : `azureuser`
- Authentification : génération de clé SSH
- Disque OS : `30 GB Standard_LRS`
- État attendu après création : `Running`

### Resolution

Le déploiement a été réalisé avec succès via Azure CLI après une phase de reconnaissance de l’environnement afin d’identifier le groupe de ressources affecté. La commande `az vm create` a permis de créer la machine virtuelle demandée sans dépendre du portail Azure, démontrant la capacité à administrer l’environnement de manière automatisée et headless.

La validation finale a été effectuée à partir de la sortie JSON de la commande, confirmant que la VM `devops-vm` était bien provisionnée et en état de fonctionnement. D’un point de vue métier, cette opération apporte trois bénéfices directs : une meilleure standardisation des déploiements, une réduction de la dépendance aux interfaces graphiques et une transition concrète vers une gestion cloud plus scriptable, gouvernable et industrialisable.

## Technical Implementation

### Topology

This task was executed as a CLI-only Azure administration workflow from the `azure-client` host, with no dependency on the Azure Portal. The implementation goal was to provision a Linux virtual machine using native Azure CLI capabilities while keeping the command concise and aligned with Azure’s implicit resource handling model.

The target VM configuration was:

- **VM name:** `devops-vm`
- **Image:** `Ubuntu2204`
- **Size:** `Standard_B2s`
- **Admin username:** `azureuser`
- **Authentication:** auto-generated SSH key pair
- **OS disk:** `30 GB`
- **Storage SKU:** `Standard_LRS`
- **Required runtime state:** `Running`

Because the lab notes indicate that resource group discovery was required beforehand, the workflow began with environment reconnaissance and then moved directly to VM creation. This is a strong example of transitioning from GUI-based cloud administration to repeatable command-line provisioning.

> [!INFO]
> Azure CLI can implicitly create supporting resources such as networking components when they are not explicitly pre-defined, which helps keep lab provisioning efficient and idiomatic.

> [!NOTE]
> The exact resource group name was discovered dynamically in the environment before running the deployment command.

### Action

The implementation followed two clear phases: identify the correct target resource group, then create the VM using a single Azure CLI command.

First, the environment was inspected from the `azure-client` host to determine the assigned resource group.

```bash file="recon-resource-group.sh"
az group list --output table
```

After identifying the correct resource group, the VM was provisioned with the exact required parameters. The command below reflects the requested headless Azure management approach and the explicit transition from portal-based administration to CLI-driven provisioning.

```bash file="create-devops-vm.sh"
az vm create \
  --resource-group <RESOURCE_GROUP_NAME> \
  --name devops-vm \
  --image Ubuntu2204 \
  --size Standard_B2s \
  --admin-username azureuser \
  --generate-ssh-keys \
  --os-disk-size-gb 30 \
  --storage-sku Standard_LRS
```

This approach intentionally avoids over-engineering. Rather than manually pre-creating every dependent component, it leverages the native behavior of `az vm create` to provision the required infrastructure when not otherwise specified.

Once the deployment completed, the JSON response was reviewed to verify successful provisioning and confirm that the VM was created in the expected running state.

```bash file="validate-vm-state.sh"
az vm get-instance-view \
  --resource-group <RESOURCE_GROUP_NAME> \
  --name devops-vm \
  --query "instanceView.statuses[].displayStatus" \
  --output table
```

> [!SUCCESS]
> The provisioning completed successfully, and the command output confirmed that the virtual machine was running.

> [!WARNING]
> Replace `<RESOURCE_GROUP_NAME>` with the actual resource group discovered in the lab before executing the creation command.

> [!DANGER]
> SSH private keys generated during provisioning must be protected and never exposed in shared repositories or unsecured systems.
