## Résumé pour la direction

### Scenario

Dans le cadre de la consolidation de données sensibles liées à une migration, l’équipe Nautilus DevOps avait besoin d’un référentiel Azure centralisé, durable et strictement contrôlé. L’objectif était de créer un espace de stockage adapté aux usages Blob tout en réduisant le risque d’exposition accidentelle des données.

Les exigences principales étaient les suivantes :

- déployer un compte de stockage Azure moderne de type **StorageV2**
- héberger les objets dans un conteneur Blob dédié
- appliquer un niveau d’accès **privé** au conteneur
- renforcer la posture de sécurité pour prévenir tout accès anonyme non autorisé

Cette opération répond à un besoin classique de gouvernance cloud : stocker des artefacts de migration dans une plateforme managée, tout en respectant les bonnes pratiques de protection des données.

### Resolution

Le déploiement a abouti à la création du compte de stockage **xfusionst9844** dans le groupe de ressources **kml_rg_main-2e7a526a32b24440** en région **East US**, ainsi qu’au conteneur Blob **xfusion-blob-17812** configuré en accès **Private**.

La configuration obtenue permet :

- une centralisation sécurisée des données sensibles
- une réduction du risque de fuite via l’accès anonyme
- une base prête pour des opérations ultérieures d’ingestion, d’archivage ou d’automatisation DevOps

La validation fonctionnelle repose sur la présence des ressources attendues et sur le fait que le conteneur n’autorise pas l’accès public.

## Technical Implementation

### Topology

The deployment was implemented in Azure as a lightweight storage security baseline for sensitive migration artifacts.

**Target resources**

- **Resource Group:** `kml_rg_main-2e7a526a32b24440`
- **Region:** `eastus`
- **Storage Account:** `xfusionst9844`
- **Kind:** `StorageV2`
- **SKU:** `Standard_LRS`
- **Blob Container:** `xfusion-blob-17812`
- **Container Access Level:** `private`

This is a headless, CLI-first deployment pattern suitable for repeatable administration and future IaC adoption. No complex networking topology was required for this task because the core objective was secure object storage provisioning with restricted blob exposure.

> [!INFO]
> **Architectural Insight — Defense in Depth**  
> Setting the container access level to `private` is necessary, but enterprise security should also disable **Blob anonymous access** at the **Storage Account** level. This creates an additional control boundary that prevents accidental public exposure caused by future container misconfiguration, scripting errors, or policy drift. In practice, account-level anonymous access disablement is a stronger data leakage prevention measure than relying only on container-level privacy.

### Action

The implementation used concise command-line automation to provision the storage account and create the private blob container. The approach favors native Azure capabilities and avoids unnecessary scripting complexity.

#### Azure CLI deployment

```bash file="deploy-storage.sh"
RG="kml_rg_main-2e7a526a32b24440"
LOCATION="eastus"
STORAGE_ACCOUNT="xfusionst9844"
CONTAINER_NAME="xfusion-blob-17812"

az storage account create \
  --name "$STORAGE_ACCOUNT" \
  --resource-group "$RG" \
  --location "$LOCATION" \
  --sku Standard_LRS \
  --kind StorageV2 \
  --allow-blob-public-access false

az storage container create \
  --name "$CONTAINER_NAME" \
  --account-name "$STORAGE_ACCOUNT" \
  --auth-mode login \
  --public-access off
```

#### Azure PowerShell deployment

```powershell file="deploy-storage.ps1"
$ResourceGroupName = "kml_rg_main-2e7a526a32b24440"
$Location = "EastUS"
$StorageAccountName = "xfusionst9844"
$ContainerName = "xfusion-blob-17812"

$storageAccount = New-AzStorageAccount `
  -ResourceGroupName $ResourceGroupName `
  -Name $StorageAccountName `
  -Location $Location `
  -SkuName Standard_LRS `
  -Kind StorageV2 `
  -AllowBlobPublicAccess $false

New-AzStorageContainer `
  -Name $ContainerName `
  -Context $storageAccount.Context `
  -Permission Off
```

#### Validation steps

```bash file="validate-storage.sh"
az storage account show \
  --name "xfusionst9844" \
  --resource-group "kml_rg_main-2e7a526a32b24440" \
  --query "{name:name,kind:kind,allowBlobPublicAccess:allowBlobPublicAccess}" \
  -o table

az storage container show \
  --name "xfusion-blob-17812" \
  --account-name "xfusionst9844" \
  --auth-mode login \
  --query "{name:name,publicAccess:properties.publicAccess}" \
  -o table
```

> [!SUCCESS]
> The final state is compliant with the requested scope: a `StorageV2` account was created, blob anonymous access was disabled at the account level, and the container was provisioned with private access.

> [!WARNING]
> If uploads will be automated later through pipelines or applications, prefer Microsoft Entra ID and RBAC over shared keys wherever possible to reduce credential management risk.

This workflow also illustrates a practical shift from portal-driven provisioning to reusable command-based deployment. While this task does not require full Infrastructure as Code, the CLI and PowerShell commands provide a clean foundation for later conversion into Bicep, Terraform, or CI/CD automation.
