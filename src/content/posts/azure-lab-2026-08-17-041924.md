## Résumé pour la direction

### Scenario
Dans le cadre de la stratégie de migration cloud progressive de l’équipe Nautilus DevOps, il était nécessaire de mettre en place une fondation réseau isolée dans Azure. L’objectif principal consistait à créer un réseau virtuel dédié ainsi qu’un sous-réseau associé afin de préparer l’intégration future de ressources de calcul, tout en conservant une séparation claire des flux réseau.

Cette étape est importante pour standardiser l’architecture de base, améliorer la gouvernance réseau et réduire les risques liés à l’exposition non contrôlée des futures charges de travail. Elle s’inscrit également dans une logique de préparation à l’industrialisation des déploiements cloud.

### Resolution
Le réseau virtuel **xfusion-vnet** a été provisionné avec succès dans la région **South Central US**, avec l’espace d’adressage **10.0.0.0/16**, ainsi que le sous-réseau dédié **xfusion-subnet**. La validation du déploiement a confirmé que la base réseau est opérationnelle et prête à accueillir les prochaines ressources de l’environnement.

La valeur métier apportée est immédiate : l’équipe dispose désormais d’un périmètre réseau sécurisé, structuré et extensible, aligné avec une montée en charge progressive des usages cloud.

> [!SUCCESS] Le socle réseau Azure a été validé avec succès et peut désormais servir de base aux futurs déploiements applicatifs et d’infrastructure.

## Technical Implementation

### Topology
The deployment targeted **South Central US** and established a dedicated Azure Virtual Network for the Nautilus DevOps migration baseline.

Provisioned parameters:
- **Virtual Network Name:** `xfusion-vnet`
- **Address Space:** `10.0.0.0/16`
- **Subnet Name:** `xfusion-subnet`

This is a straightforward foundational network build intended for future workload onboarding. The design keeps the network layer simple and clean, which is appropriate for early-stage cloud migration patterns.

![Azure Configuration](@/assets/images/azure-task-20260817-041911.webp)

> [!INFO] This provisioning can be performed in a fully headless manner using Azure CLI or Azure PowerShell, making it suitable for automation pipelines and Infrastructure as Code workflows.

### Action
The implementation consisted of provisioning a new Virtual Network and defining a dedicated subnet during creation. For this type of task, using command-line tooling is preferable over manual portal configuration because it improves repeatability, auditability, and future CI/CD integration.

A concise IaC-minded approach was used:
1. Define the target region.
2. Create the Virtual Network with the required IPv4 address space.
3. Create the subnet as part of the VNet provisioning workflow.
4. Validate the deployed network configuration.

> [!NOTE] Azure native commands already support efficient resource creation patterns, so the provisioning script should remain minimal and avoid unnecessary complexity.

#### Azure CLI
```bash file="provision-vnet-subnet.sh"
az network vnet create \
  --resource-group <RESOURCE_GROUP_NAME> \
  --name xfusion-vnet \
  --location southcentralus \
  --address-prefixes 10.0.0.0/16 \
  --subnet-name xfusion-subnet
```

#### Azure PowerShell
```powershell file="provision-vnet-subnet.ps1"
New-AzVirtualNetwork `
  -ResourceGroupName "<RESOURCE_GROUP_NAME>" `
  -Name "xfusion-vnet" `
  -Location "South Central US" `
  -AddressPrefix "10.0.0.0/16" `
  -Subnet @(New-AzVirtualNetworkSubnetConfig -Name "xfusion-subnet" -AddressPrefix "10.0.0.0/24")
```
