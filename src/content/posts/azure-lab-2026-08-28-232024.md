## Résumé pour la direction

### Scenario
L’équipe Nautilus DevOps cherche à standardiser le provisionnement réseau dans Azure en adoptant une approche Infrastructure as Code (IaC). L’objectif est de remplacer les créations manuelles ou semi-manuelles par un modèle déclaratif, versionné et réutilisable, afin de garantir des déploiements homogènes entre les environnements.

Dans ce cas, le besoin portait sur le déploiement d’un réseau virtuel Azure nommé **arm-vnet-datacenter** avec une plage d’adressage **192.168.0.0/16**, tout en appliquant les standards de marquage de l’entreprise avec les tags **displayName=arm-vnet-datacenter** et **Environment=KKE-datacenter**.

Cette démarche répond à plusieurs enjeux métiers : amélioration de la gouvernance cloud, réduction des écarts de configuration, facilitation des contrôles de conformité et accélération des opérations de déploiement grâce à des composants réutilisables et audités.

### Resolution
Le réseau virtuel a été défini dans un modèle ARM mis à jour puis déployé via Azure CLI selon une approche entièrement déclarative. Le résultat obtenu est un provisionnement cohérent, reproductible et aligné sur les standards de nommage et de tagging attendus.

La validation du déploiement confirme que la ressource **arm-vnet-datacenter** a bien été créée avec la plage CIDR demandée et les métadonnées d’entreprise associées. Cette mise en œuvre apporte une valeur directe en matière de traçabilité, de qualité de changement, et de réduction du risque de dérive de configuration entre les environnements Azure.

## Technical Implementation

### Topology
The target architecture is intentionally simple and focused on network standardization through declarative deployment. The solution provisions a single Azure Virtual Network with the following parameters:

- **Resource type:** `Microsoft.Network/virtualNetworks`
- **Virtual network name:** `arm-vnet-datacenter`
- **Address space:** `192.168.0.0/16`
- **Tags:**
  - `displayName=arm-vnet-datacenter`
  - `Environment=KKE-datacenter`

The deployment is executed headlessly through **Azure CLI**, with the infrastructure definition stored in a JSON ARM template. This approach makes the network configuration deterministic and suitable for source control, CI/CD pipelines, and change reviews.

![Azure Configuration](@/assets/images/azure-task-20260828-232008.webp)

> [!INFO]
> **Architectural Insight:** Declarative IaC such as ARM, Bicep, or Terraform is superior to imperative GUI/CLI creation because the desired end state is explicitly documented in code. This improves state tracking, enables peer review through pull requests, and reduces configuration drift by ensuring environments are rebuilt from the same reviewed definition instead of relying on manual operator actions.

### Action
The implementation consisted of updating an existing ARM template to align with the required CIDR block and corporate tagging standards, then deploying it using Azure CLI.

A concise and production-friendly pattern is to keep the ARM template parameterized so the same file can be reused across environments with minimal changes.

```json file="azuredeploy.json"
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "vnetName": {
      "type": "string",
      "defaultValue": "arm-vnet-datacenter",
      "metadata": {
        "description": "Name of the Azure Virtual Network."
      }
    },
    "location": {
      "type": "string",
      "defaultValue": "[resourceGroup().location]",
      "metadata": {
        "description": "Azure region for the deployment."
      }
    },
    "addressPrefix": {
      "type": "string",
      "defaultValue": "192.168.0.0/16",
      "metadata": {
        "description": "CIDR block for the virtual network."
      }
    },
    "displayNameTag": {
      "type": "string",
      "defaultValue": "arm-vnet-datacenter",
      "metadata": {
        "description": "Corporate display name tag."
      }
    },
    "environmentTag": {
      "type": "string",
      "defaultValue": "KKE-datacenter",
      "metadata": {
        "description": "Corporate environment tag."
      }
    }
  },
  "resources": [
    {
      "type": "Microsoft.Network/virtualNetworks",
      "apiVersion": "2023-09-01",
      "name": "[parameters('vnetName')]",
      "location": "[parameters('location')]",
      "tags": {
        "displayName": "[parameters('displayNameTag')]",
        "Environment": "[parameters('environmentTag')]"
      },
      "properties": {
        "addressSpace": {
          "addressPrefixes": [
            "[parameters('addressPrefix')]"
          ]
        }
      }
    }
  ],
  "outputs": {
    "virtualNetworkName": {
      "type": "string",
      "value": "[parameters('vnetName')]"
    },
    "virtualNetworkAddressPrefix": {
      "type": "string",
      "value": "[parameters('addressPrefix')]"
    }
  }
}
```

The Azure CLI deployment script below creates the resource group if needed, validates the template, and deploys it. The script stays intentionally lean and relies on native Azure CLI capabilities rather than overcomplicating the workflow.

```bash file="deploy-vnet.sh"
#!/usr/bin/env bash
set -euo pipefail

RESOURCE_GROUP="rg-nautilus-network"
LOCATION="eastus"
DEPLOYMENT_NAME="deploy-arm-vnet-datacenter"
TEMPLATE_FILE="azuredeploy.json"

az group create \
  --name "$RESOURCE_GROUP" \
  --location "$LOCATION"

az deployment group validate \
  --resource-group "$RESOURCE_GROUP" \
  --name "${DEPLOYMENT_NAME}-validate" \
  --template-file "$TEMPLATE_FILE"

az deployment group create \
  --resource-group "$RESOURCE_GROUP" \
  --name "$DEPLOYMENT_NAME" \
  --template-file "$TEMPLATE_FILE"
```

After deployment, the resource can be verified with a lightweight query:

```bash file="verify-vnet.sh"
#!/usr/bin/env bash
set -euo pipefail

RESOURCE_GROUP="rg-nautilus-network"
VNET_NAME="arm-vnet-datacenter"

az network vnet show \
  --resource-group "$RESOURCE_GROUP" \
  --name "$VNET_NAME" \
  --query "{name:name,addressSpace:addressSpace.addressPrefixes,tags:tags}" \
  --output table
```

> [!SUCCESS]
> The final state is reproducible: the same template can be committed to source control, reviewed by peers, and redeployed consistently across environments without relying on manual portal steps.

> [!WARNING]
> Keep naming, CIDR planning, and tagging conventions aligned with enterprise governance rules before promoting the template into shared CI/CD pipelines.
