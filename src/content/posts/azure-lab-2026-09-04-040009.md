## Table of Contents

## Résumé pour la direction

### Scenario

Dans ce laboratoire, l’objectif était de rétablir l’accessibilité publique d’une machine virtuelle Azure hébergée dans le réseau virtuel **nautilus-vnet** en région **West US**, puis d’y publier un service web Nginx. Le dysfonctionnement principal provenait d’une configuration réseau incohérente entre le routage sortant, l’exposition publique de la machine et les règles de sécurité.

Le point critique était la présence d’une route définie par l’utilisateur (UDR) configurée en **blackhole routing**, c’est-à-dire avec un **Next Hop** positionné sur **None** pour la route par défaut `0.0.0.0/0`. Dans un contexte d’entreprise, ce type de configuration bloque volontairement tout trafic correspondant à la route, mais devient problématique si la machine virtuelle doit être publiée sur Internet pour un usage d’administration ou d’hébergement web.

Les exigences de la tâche étaient les suivantes :

- corriger le routage pour restaurer une sortie réseau valide ;
- associer une **IP publique** à la machine virtuelle ;
- autoriser le trafic HTTP entrant sur le **port 80** ;
- installer et démarrer **Nginx** pour valider le bon fonctionnement de bout en bout.

> [!INFO]
> La correction attendue consistait à **mettre à jour la route UDR** pour faire pointer `0.0.0.0/0` vers **Internet**, et non à supprimer la table de routage. Cette approche respecte une logique d’exploitation propre et maîtrisée.

### Resolution

La remédiation a été réalisée avec succès sur l’environnement **West US** comprenant **nautilus-vnet**, **nautilus-vm** et **nautilus-pip**. Les quatre actions de dépannage ont été exécutées dans l’ordre logique :

1. correction du routage UDR en remplaçant le **Next Hop: None** par **Internet** ;
2. association de **nautilus-pip** à la carte réseau de **nautilus-vm** ;
3. ouverture du **port 80** dans le NSG ;
4. connexion SSH à la VM pour installer et lancer **Nginx**.

Le résultat final a permis de restaurer la connectivité publique et de servir une page web via HTTP. La validation fonctionnelle confirme que l’architecture réseau est de nouveau cohérente entre routage, adressage public, filtrage réseau et service applicatif.

La valeur métier apportée est double :

- rétablissement rapide d’un service exposé publiquement ;
- application d’une correction réseau conforme aux bonnes pratiques d’exploitation Azure, sans suppression abusive de composants de gouvernance existants.

## Technical Implementation

### Topology

The environment was deployed in **West US** and centered around these core Azure resources:

- **Virtual Network:** `nautilus-vnet`
- **Virtual Machine:** `nautilus-vm`
- **Public IP:** `nautilus-pip`

The troubleshooting scope covered four layers of the stack:

1. **Routing layer**: a User-Defined Route was configured with `0.0.0.0/0 -> None`, effectively blackholing default traffic.
2. **Public exposure layer**: the VM NIC did not have the expected public IP association.
3. **Security layer**: inbound HTTP on port 80 was not allowed through the NSG.
4. **Application layer**: Nginx had to be installed and started on the VM.

This was a practical Azure networking and compute validation exercise that can be executed through the portal, but the operational mindset should favor repeatable command-line or IaC-driven corrections where possible.

#### Architectural Insight

**Blackhole routing** occurs when traffic is intentionally sent to a non-forwarding destination. In Azure UDR terms, setting the route for `0.0.0.0/0` with **Next hop type: None** discards matching traffic instead of forwarding it. This is sometimes used for strict traffic control, segmentation, or forced egress restrictions.

In this case, the route prevented valid default-path communication. The proper enterprise fix was to **update the existing UDR** so that:

- **Address Prefix:** `0.0.0.0/0`
- **Next Hop Type:** `Internet`

This is the correct remediation because it preserves the route table as a managed network control object while restoring intended outbound behavior. Deleting the route table would be a poor operational choice because it removes governance structure instead of correcting the faulty rule inside it.

> [!WARNING]
> Removing an entire route table may introduce uncontrolled routing behavior and drift from enterprise network standards. Adjust the offending route, not the governance object.

### Action

The troubleshooting and validation sequence followed these four explicit steps.

#### 1. Fix the blackhole route

The first issue was the UDR default route configured with **Next hop: None**. That setting dropped all traffic matching `0.0.0.0/0`. The route was updated so the next hop became **Internet**, restoring proper default egress behavior.

```bash file="fix-udr-route.sh"
az network route-table route update \
  --resource-group <resource-group> \
  --route-table-name <route-table-name> \
  --name <route-name> \
  --address-prefix 0.0.0.0/0 \
  --next-hop-type Internet
```

This was the cleanest fix because it preserved the route table association and changed only the incorrect forwarding behavior.

> [!SUCCESS]
> Updating the UDR in place is a precise and auditable network correction aligned with enterprise change practices.

#### 2. Associate the public IP to the VM NIC

The second issue was that `nautilus-vm` was not reachable publicly because `nautilus-pip` had not been associated with the VM network interface IP configuration. The public IP was attached to the NIC to enable external access.

```bash file="associate-public-ip.sh"
az network nic ip-config update \
  --resource-group <resource-group> \
  --nic-name <nic-name> \
  --name ipconfig1 \
  --public-ip-address nautilus-pip
```

This step established the public entry point required for SSH administration and HTTP testing.

#### 3. Open port 80 in the NSG

After public IP association, inbound HTTP still required an explicit NSG rule. Port 80 was allowed so the Nginx web server could be reached from the Internet.

```bash file="allow-http-nsg.sh"
az network nsg rule create \
  --resource-group <resource-group> \
  --nsg-name <nsg-name> \
  --name allow-http-80 \
  --priority 1000 \
  --direction Inbound \
  --access Allow \
  --protocol Tcp \
  --destination-port-ranges 80
```

This rule enabled browser-based validation of the web service once the application was installed.

> [!NOTE]
> In real environments, source IP ranges should be restricted whenever possible instead of allowing overly broad inbound access.

#### 4. SSH into the VM and install Nginx

With routing, public IP, and NSG configuration corrected, the VM became accessible over SSH. Nginx was then installed and started to validate full-stack connectivity.

```bash file="install-nginx.sh"
ssh azureuser@<public-ip> <<'EOF'
sudo apt-get update
sudo apt-get install -y nginx
sudo systemctl enable nginx
sudo systemctl start nginx
sudo systemctl status nginx --no-pager
EOF
```

For Ubuntu-based Azure VMs, this is a concise and idiomatic setup path. It confirms:

- SSH reachability
- outbound package access
- successful package installation
- active HTTP service on port 80

A final browser or curl test can be used to verify the default Nginx page.

```bash file="validate-http.sh"
curl http://<public-ip>
```

If the default Nginx landing page is returned, the remediation is complete.

> [!INFO]
> This sequence demonstrates a common transition from GUI troubleshooting to command-based operations, which is a foundational step toward Infrastructure as Code and repeatable cloud remediation workflows.
