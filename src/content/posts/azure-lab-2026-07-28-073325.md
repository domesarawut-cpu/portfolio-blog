## Résumé pour la direction

### Scenario

Dans le cadre du durcissement de la sécurité des accès aux machines virtuelles Azure, l’objectif de cette tâche était de remplacer l’authentification par mot de passe par une authentification basée sur une paire de clés SSH. Cette approche répond à un besoin classique de réduction de la surface d’attaque, en particulier contre les tentatives d’accès non autorisées et les attaques par force brute.

La demande consistait à créer, via l’interface **Azure Portal**, une paire de clés SSH de type **RSA** nommée **`devops-kp`**, rattachée au **Resource Group** **`kml_rg_main-1a5bc94f5c944ba3`**. Une exigence importante du processus était la récupération immédiate de la **clé privée au format `.pem`** sur le poste client, Azure ne conservant pas cette clé privée après la génération.

### Resolution

La création de la paire de clés SSH **RSA** a été réalisée avec succès dans Azure Portal, avec le nom **`devops-kp`** et l’association au groupe de ressources **`kml_rg_main-1a5bc94f5c944ba3`**. La validation de configuration a affiché le statut **“Validation passed”** en vert, confirmant la conformité des paramètres saisis.

Le résultat apporte une valeur directe en matière de sécurité : l’accès futur aux machines virtuelles pourra s’appuyer sur une authentification asymétrique plus robuste que le mot de passe. La clé privée a bien été téléchargée localement sur le poste client, conformément au modèle de sécurité Azure, ce qui garantit que le secret d’authentification reste sous le contrôle exclusif de l’utilisateur ou de l’équipe d’exploitation.

## Technical Implementation

### Topology

The implementation used **Azure Portal** to generate an **RSA SSH key pair** for future Azure Virtual Machine access. The key resource was created under the following scope:

- **Resource Group:** `kml_rg_main-1a5bc94f5c944ba3`
- **SSH Key Name:** `devops-kp`
- **Key Type:** `RSA`
- **Provisioning Method:** Azure Portal
- **Security Objective:** Replace password authentication with SSH key-based authentication

From an architectural standpoint, the generated SSH key pair supports a standard Azure VM access model:

- The **public key** is stored in Azure and can later be injected into a Linux VM during creation or configuration.
- The **private key** is downloaded as a **`.pem`** file to the client machine.
- Azure does **not** retain the private key after generation, which enforces client-side secret custody.

> [!INFO]
> Azure stores the public component for VM authentication workflows, but the private key must be securely preserved by the administrator on the client side.

> [!WARNING]
> If the downloaded `.pem` file is lost and no backup exists, Azure cannot recover it. A new SSH key pair must be created and redistributed.

### Action

The task was completed through the **Azure Portal web interface** with the following execution details:

1. Opened **Azure Portal** and navigated to the SSH key creation workflow.
2. Selected the target **Resource Group**:
   - `kml_rg_main-1a5bc94f5c944ba3`
3. Entered the SSH key name:
   - `devops-kp`
4. Chose the **RSA** algorithm as required by the lab instructions.
5. Reviewed the configuration and confirmed that the portal displayed:
   - **Validation passed**
6. Submitted the configuration to create the SSH key pair.
7. Downloaded the generated **private key file (`.pem`)** immediately to the client machine.
8. Confirmed that the private key was stored locally, acknowledging that Azure would not keep a retrievable copy.

The resulting configuration can be summarized as follows:

```text file="ssh-key-configuration.txt"
Resource Group : kml_rg_main-1a5bc94f5c944ba3
SSH Key Name   : devops-kp
Key Algorithm  : RSA
Access Method  : SSH key-based authentication
Portal Status  : Validation passed
Private Key    : Downloaded as .pem to client machine
```

Although this task was performed in the web portal, the effective operational outcome aligns with the following security model:

```bash file="security-principle.sh"
# Intended authentication model for future Linux VM access
ssh -i devops-kp.pem azureuser@<public-ip-or-dns>
```

> [!TIP]
> Store the `.pem` file in a protected client-side location with restricted file permissions, and never commit private keys to source control repositories.

> [!DANGER]
> Anyone with access to the private key file may be able to authenticate to associated virtual machines. Protect the file with strict endpoint security controls.

The green **Validation passed** status confirmed that the naming, resource group selection, and key type were all accepted before deployment, reducing the risk of provisioning errors and ensuring readiness for subsequent VM integration.
